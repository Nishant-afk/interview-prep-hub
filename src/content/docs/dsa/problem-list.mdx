## Why it matters in interviews

At 3-4 years you will usually get one or two easy-to-medium problems in 30-45 minutes. Interviewers rarely reuse a famous problem word for word, but almost every question is a **variation of a pattern** below. Solving these 77 problems, grouped by pattern, teaches you to recognise the pattern in a new question, which is the real skill being tested.

## How to use this list

1. **Learn the pattern first.** Read the linked page, then solve the problems in that group in order (they get harder).
2. **Time-box.** 25 minutes for an Easy, 40 for a Medium. If stuck, read the key idea below, not the full solution, and try again.
3. **Say the complexity** before you run the code, and compare it to the target column.
4. **Re-solve after a week** without notes. Problems marked ⭐ are the core set if you only have two weeks.
5. Solve in **C#** first; redo the ⭐ problems in TypeScript if you are interviewing for full-stack roles.

<Aside type="tip" title="Tracking progress">
The Done boxes are for the current session only and reset when you reload. Use the page's progress button to mark the whole list, or copy the tables into your own notes.
</Aside>

## Interview Q&A

<details>
<summary>How many problems should I solve before interviewing?</summary>

Quality beats count. Solving these ~75 properly (pattern understood, complexity stated, re-solved a week later) is worth more than rushing through 300. If you can solve a new Medium in a pattern you know within 30-40 minutes, move on to the next pattern.
</details>

<details>
<summary>I am stuck on a problem. When should I read the solution?</summary>

After about 25-40 minutes of genuine attempts. Read the key idea first, then try again. If you still need the full solution, write it yourself from memory afterwards, and add the problem to a "redo" list for next week.
</details>

<details>
<summary>What should I say in the first two minutes of a coding interview?</summary>

Restate the problem, ask about input size, duplicates, negatives, empty input and expected output format, then walk through a small example. State a brute-force approach and its complexity before optimising. Interviewers grade the communication as much as the final code.
</details>

<details>
<summary>Should I practise in C# or TypeScript?</summary>

Use the language you are strongest in, usually C# for a .NET role. Know the standard library well: `Dictionary`, `HashSet`, `Queue`, `Stack`, `PriorityQueue`, `Array.Sort` with a comparison, `List.BinarySearch`. For full-stack roles, be able to write the ⭐ problems in TypeScript too, remembering that JS has no built-in heap and that `.sort()` compares as strings by default.
</details>

## Pitfalls

<Aside type="caution" title="Common practice mistakes">
- Grinding problems in random order instead of by pattern.
- Reading the solution after five minutes, then "recognising" it later and mistaking that for learning.
- Never stating complexity, or only stating time and forgetting space.
- Skipping edge cases: empty input, single element, duplicates, negatives, overflow.
- Practising only in an IDE with autocomplete. Do some problems in a plain editor, since many interviews use one.
</Aside>
