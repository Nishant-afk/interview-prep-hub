## Why it matters in interviews

*"How do you store passwords?"*, *"hashing vs encryption?"*, *"where do you keep the connection string in production?"* are quick filters. Answers like "encrypt the passwords with AES" or "Base64 the API key" end the discussion badly. A good answer names the primitive, the .NET API, and where the keys live.

## Core idea

### Hashing vs encryption vs encoding

| | Encoding | Hashing | Encryption |
|---|---|---|---|
| Purpose | Represent data in another format | Fingerprint / verify without storing the original | Confidentiality: only key holders can read |
| Reversible? | Yes, by anyone | **No** (one-way) | Yes, **with the key** |
| Key? | None | None (HMAC uses a key for integrity) | Symmetric or asymmetric key |
| Examples | Base64, base64url, URL encoding, UTF-8 | SHA-256, SHA-512; for passwords PBKDF2, bcrypt, scrypt, Argon2 | AES-GCM, RSA-OAEP, ChaCha20-Poly1305 |
| Security value | **None** | Integrity, password verification | Confidentiality (AEAD modes also give integrity) |
| .NET | `Convert.ToBase64String`, `Base64Url` | `SHA256.HashData`, `HMACSHA256.HashData`, `Rfc2898DeriveBytes.Pbkdf2` | `AesGcm`, `RSA`, Data Protection API |

A JWT payload is **encoded**, a password is **hashed**, a credit card number at rest is **encrypted**.

### Password hashing

Passwords must be **hashed with a slow, salted, password-specific algorithm**, never encrypted (if the key leaks, every password leaks) and never a plain fast hash.

- **Salt**: random per-user bytes stored next to the hash. Identical passwords get different hashes, which defeats precomputed rainbow tables.
- **Work factor**: iterations or memory cost make each guess expensive. SHA-256 runs billions of times per second on a GPU; PBKDF2 with hundreds of thousands of iterations does not.
- **Constant-time comparison** (`CryptographicOperations.FixedTimeEquals`) avoids timing leaks.

| Algorithm | Notes |
|---|---|
| **Argon2id** | OWASP's first choice; memory-hard (resists GPUs/ASICs). Needs a third-party package in .NET |
| **scrypt** | Memory-hard, fine alternative |
| **bcrypt** | Mature and widely used; 72-byte input limit |
| **PBKDF2** | NIST-approved, built into .NET; needs high iterations (OWASP suggests 600,000 for HMAC-SHA256 or 210,000 for HMAC-SHA512) |

**ASP.NET Core Identity's `PasswordHasher<TUser>`** uses PBKDF2 with a random 128-bit salt. Its current (V3) format uses **HMAC-SHA512 with 100,000 iterations** by default (.NET 7 and later; older versions used HMAC-SHA256 with 10,000). The algorithm and iteration count are stored inside the hash, so `VerifyHashedPassword` returns `SuccessRehashNeeded` when you raise the settings, letting you upgrade hashes at next login.

### Symmetric vs asymmetric

| | Symmetric | Asymmetric |
|---|---|---|
| Keys | One shared secret key | Public/private key pair |
| Speed | Fast, any data size | Slow, small payloads |
| Algorithms | AES-GCM (AES-256), ChaCha20-Poly1305 | RSA (2048+ bits), ECDSA / ECDH (P-256), Ed25519 |
| Used for | Bulk data encryption, field encryption, TLS session data | Key exchange, digital signatures (JWT RS256), certificates |
| Problem | Distributing the key safely | Performance; trusting public keys (PKI) |

Real systems combine them (**hybrid encryption**): asymmetric to agree on or wrap a key, symmetric for the data. TLS and Key Vault "envelope encryption" both work this way.

Use **authenticated encryption** (AES-GCM): it detects tampering. Avoid ECB, and avoid CBC without a MAC. Never reuse a GCM nonce with the same key.

### TLS and certificates

HTTPS = HTTP over **TLS**. During the handshake the server presents an **X.509 certificate** (its public key signed by a certificate authority); client and server do an ephemeral key exchange (ECDHE) and derive **symmetric session keys**. TLS gives confidentiality, integrity and server authentication.

- Use TLS 1.2+ (prefer 1.3); terminate at the load balancer, App Service or ingress, and re-encrypt to the back end where policy requires.
- **HSTS** (`UseHsts()`) tells browsers to always use HTTPS for your domain.
- Managed certificates: App Service managed certs, Key Vault certificates (AWS: ACM). **mTLS** adds client certificates for service-to-service.

### Data Protection API

ASP.NET Core's **Data Protection** encrypts and signs short-lived payloads: auth cookies, antiforgery tokens, TempData, and your own values (password-reset links, unsubscribe tokens). It manages a **key ring** with automatic rotation (90 days by default). Use **purpose strings** to isolate protectors.

In a web farm or containers, keys must be **shared and persisted** (blob storage, Redis, DB) and protected at rest (Key Vault). Otherwise each instance or restart has different keys and users get logged out or see antiforgery errors.

### Secrets: Key Vault and managed identity

Secrets (connection strings, API keys, signing keys) don't belong in source code, `appsettings.json`, Docker images or the Angular bundle.

| Environment | Where secrets live |
|---|---|
| Local dev | `dotnet user-secrets` (outside the repo; not encrypted, dev only) |
| CI/CD | Pipeline secret variables / GitHub Actions secrets, or OIDC federation to the cloud |
| Production | **Azure Key Vault** (AWS: **Secrets Manager** / SSM Parameter Store, keys in **KMS**) |

**Managed identity** gives the app an Entra ID identity managed by Azure, so it can get tokens for Key Vault, SQL or Storage **without any secret**. Grant it least-privilege RBAC roles (e.g. *Key Vault Secrets User*). In code, `DefaultAzureCredential` uses managed identity in Azure and your developer login locally. AWS equivalent: an **IAM role** attached to the EC2 instance, ECS task or Lambda.

Better still, avoid secrets entirely: SQL with Entra authentication via managed identity, storage with RBAC instead of account keys.

var result = hasher.VerifyHashedPassword(user, user.PasswordHash, attempt);

### Encrypting a field with AES-GCM

```csharp
public static byte[] Encrypt(byte[] key, byte[] plaintext, byte[] associatedData)
{
    var nonce = RandomNumberGenerator.GetBytes(AesGcm.NonceByteSizes.MaxSize); // 12 bytes, unique per key
    var tag = new byte[AesGcm.TagByteSizes.MaxSize];                         // 16 bytes
    var cipher = new byte[plaintext.Length];
    using var aes = new AesGcm(key, tag.Length);                              // 32-byte key = AES-256
    aes.Encrypt(nonce, plaintext, cipher, tag, associatedData);
    return [.. nonce, .. tag, .. cipher];
}

public static byte[] Decrypt(byte[] key, byte[] blob, byte[] associatedData)
{
    var plain = new byte[blob.Length - 28];
    using var aes = new AesGcm(key, 16);
    aes.Decrypt(blob.AsSpan(0, 12), blob.AsSpan(28), blob.AsSpan(12, 16), plain, associatedData);
    return plain; // Decrypt throws if anything was tampered with
}
```

`associatedData` (for example the row id) is authenticated but not encrypted, so a ciphertext can't be copied onto another row. The key itself comes from Key Vault, ideally wrapped by a Key Vault key (envelope encryption). For SQL Server columns, **Always Encrypted** is the managed alternative.

### Data Protection

```csharp
builder.Services.AddDataProtection()
    .SetApplicationName("orders") // same name on every instance
    .PersistKeysToAzureBlobStorage(new Uri("https://storders.blob.core.windows.net/dp/keys.xml"),
        new DefaultAzureCredential())
    .ProtectKeysWithAzureKeyVault(new Uri("https://kv-orders.vault.azure.net/keys/dp-key"),
        new DefaultAzureCredential());

public class UnsubscribeLinks(IDataProtectionProvider provider)
{
    private readonly ITimeLimitedDataProtector _protector =
        provider.CreateProtector("Orders.UnsubscribeLink.v1").ToTimeLimitedDataProtector();

    public string Create(string userId) => _protector.Protect(userId, TimeSpan.FromDays(7));
    public string Read(string token) => _protector.Unprotect(token); // throws if tampered or expired
}
```

## Interview Q&A

<details>
<summary>What is the difference between hashing, encryption and encoding?</summary>

**Encoding** changes representation and is reversible by anyone (Base64): no security. **Hashing** is one-way and fixed length: used to verify (passwords, integrity). **Encryption** is reversible only with a key: used for confidentiality. Rule of thumb: store passwords hashed, sensitive data encrypted, and never call Base64 "encryption".
</details>

<details>
<summary>How do you store user passwords in an ASP.NET Core app?</summary>

Use **ASP.NET Core Identity's `PasswordHasher`** (PBKDF2-HMAC-SHA512, salted, 100,000 iterations by default in .NET 7+, tunable) or a vetted Argon2id/bcrypt library. Never store plain text, never encrypt, never use a bare SHA-256/MD5. Add rate limiting, lockout, breached-password checks and MFA around it.
</details>

<details>
<summary>What is a salt, and is it secret?</summary>

A random value generated per password and stored alongside the hash. It is **not secret**. It ensures identical passwords produce different hashes and makes precomputed tables useless, forcing attackers to crack each hash separately. A **pepper** is an extra application-wide secret (kept in Key Vault) mixed in, so a DB-only leak isn't enough.
</details>

<details>
<summary>Why not encrypt passwords so you can email them back to users?</summary>

Because anyone with the key (an insider, an attacker who compromises the server) can decrypt all of them, and users reuse passwords across sites. Systems should never be able to recover a password. Offer a **reset** flow with a single-use, time-limited token instead.
</details>

<details>
<summary>Symmetric vs asymmetric encryption: where is each used in a typical web app?</summary>

**Asymmetric**: TLS key exchange and certificates, JWT signatures (RS256: IdP signs with the private key, APIs verify with the public key), code signing. **Symmetric**: TLS bulk traffic after the handshake, AES-GCM field encryption, Data Protection payloads, HS256 tokens. Asymmetric solves key distribution; symmetric is fast.
</details>

<details>
<summary>What is the ASP.NET Core Data Protection API, and what breaks in a web farm?</summary>

A built-in API for encrypting and authenticating payloads with automatically rotated keys; it protects auth cookies and antiforgery tokens. Each instance generates its own key ring by default, so behind a load balancer a cookie made by instance A can't be read by instance B. Fix: persist keys to shared storage (Blob, Redis, DB) with a common application name and protect them with Key Vault.
</details>

<details>
<summary>How does your app read secrets in production without storing any credential?</summary>

Enable a **managed identity** on the App Service, Container App or AKS workload (via workload identity), grant it *Key Vault Secrets User* on the vault, and use `DefaultAzureCredential` with the Key Vault configuration provider. The platform issues tokens for that identity, so there's no bootstrap secret. AWS: an IAM role on the task/instance with `secretsmanager:GetSecretValue` permission.
</details>

<details>
<summary>What does HTTPS actually protect, and what doesn't it protect?</summary>

It protects data **in transit**: confidentiality, integrity and server identity against network attackers. It does nothing about data at rest, a compromised server, XSS, SQL injection or a malicious authenticated user. Hence HTTPS + HSTS is necessary but never sufficient.
</details>

## Pitfalls

<Aside type="caution" title="Common mistakes">

- Calling **Base64** encryption, or storing secrets Base64-encoded in config.
- **MD5/SHA-1/plain SHA-256** for passwords, or a global salt.
- Writing your own crypto, **ECB mode**, or reusing an AES-GCM **nonce**.
- Comparing hashes or tokens with `==` instead of `FixedTimeEquals`.
- Secrets in `appsettings.json`, Git history, Docker images, pipeline logs or `environment.ts`.
- Data Protection keys **not persisted** in containers, causing random logouts after deploys.
- One Key Vault access policy giving the app **full** permissions instead of read-only on secrets.
- Using `System.Random` for tokens. Use `RandomNumberGenerator`.

</Aside>
